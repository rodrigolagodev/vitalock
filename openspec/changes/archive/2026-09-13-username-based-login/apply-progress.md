## Deviations from Design

1. **`identity.staff.username` column DEFAULT (not in design.md)** — design.md only specifies a one-time backfill for pre-existing rows; it does not address that ~26 existing pgTAP fixtures and `supabase/seed-users.sql` insert `identity.staff` rows without a `username` column at all. Making the column `NOT NULL` with no default would have broken every one of those fixtures and `supabase db reset` itself. Added `ALTER COLUMN username SET DEFAULT ('staff-' || left(gen_random_uuid()::text, 8))` — same fallback shape design.md already uses for the backfill's null/short-email branch, satisfies NOT NULL + format + uniqueness for any writer that omits `username`. Every real application write path (`useMutateStaff.createStaff`) always supplies `username` explicitly, so the default is a fixture/test safety net only, never exercised by the app. Full 46-file pgTAP suite passes unchanged with this default in place.
2. **`supabase/seed-users.sql` edited** — added `username: 'admin'` / `'installer'` to the two dev-seed `INSERT`s. Required once the column is `NOT NULL`; this is the local-only dev/E2E seed script (`db push` never runs it), not the app's `auth.users` provisioning flow, so it does not conflict with the "don't touch auth.users provisioning" constraint.
3. **`isDuplicateUsernameError` lives in `apps/admin/src/lib/errors/toast.ts` as a standalone exported predicate, not inside `adminExtraHandlers['23505']`** — the existing `ExtraHandlersMap` type (`(err) => string | undefined`) can only produce a toast string; it cannot call `StaffFormSheet`'s `setError`. Task 7.6's "instead of the generic toast" requirement can only be satisfied by branching in the component (which owns the form's `setError`) _before_ calling `toastMutationError`. Kept the constraint-name knowledge (`staff_username_key`) in `toast.ts` per the task's file pointer; the routing decision (inline vs. toast) is in `StaffFormSheet.tsx`.
4. **`AppShell.test.tsx`, `apps/installer/src/__tests__/App.test.tsx`, `.../DashboardPage.test.tsx`, `usePersonal.test.ts` updated** — none of these are named in tasks.md, but all four broke as a direct, mechanical consequence of mandated type/prop changes (`StaffProfile.username` now required; `UserMenuProps.email`→`subtitle`; `usePersonal`'s new `row.username.toLowerCase()` call throwing on a fixture missing that field). Fixed to keep the full gate green; no unrelated behavior changed in any of them.

## Issues Found

- `apps/admin/src/hooks/usePersonal.ts`'s new `row.username.toLowerCase().includes(q)` search-filter term threw a `TypeError` for any search string that didn't already match on `id`/`full_name` (short-circuiting `||` masked it for matching cases) — caught by the existing `usePersonal.test.ts`'s "search with no match returns an empty list" case once its fixture lacked `username`. Fixed by adding `username` to the test fixture; not a defect in the shipped filter logic itself (a real `StaffRow` always has `username`), but confirms the fixture needed the same collateral update as the type change required everywhere else.
