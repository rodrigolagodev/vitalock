# Exploration — equipment-update-bundle-flow

**Slug**: `equipment-update-bundle-flow`
**Persistence**: Engram id=266 (`sdd/equipment-update-bundle-flow/explore`) + this file
**Date**: 2026-08-27

## One-line intent

Wire `resolve_equipment_update` so it advances `key_order_items.status='installed'` when a linked key is activated, and add UI to (a) generate the pending-keys snapshot per equipment (3 groups: to activate / to disable / unchanged), (b) show equipment update history with .mdb download for rollback.

## Current State — the confirmed gap

**`resolve_equipment_update` lines 113–116** (migration `20260818000072_resolve_equipment_update_v2_return.sql`):

```sql
if v_order_item_id is not null then
  select order_id into v_order_id from public.order_items where id = v_order_item_id;
  ...
end if;
```

`v_order_item_id` comes from `rfid_keys.order_item_id`. For all new-path keys (created via `configure_key_order_item` on the `key_order_items` path), `rfid_keys.order_item_id` is intentionally NULL — the new path tracks the link via `key_order_items.produced_key_id` instead. So this branch never executes for new-path keys, and `key_order_items.status` is never advanced to `installed`.

The correct join path already exists in the DB:

```
rfid_keys.id → key_order_items.produced_key_id → key_order_items.order_id
```

`mark_key_order_item_installed` (`supabase/migrations/20260823000097_key_orders_installation_stage.sql:153`) is already correct. It advances the item status and the 4-lane recompute trigger fires automatically. But it has zero UI callers. It does NOT need to become a UI action — the right place to call it is *inside `resolve_equipment_update`*, not from the frontend.

`recompute_key_order_status` (the 4-lane machine, migration 097) is triggered by `AFTER UPDATE OF status on key_order_items`. It correctly handles partial activation: if only some items are installed, the order stays in `pending_installation`. Do not modify it.

`support.equipment_updates` already stores `mdb_storage_path`, `resolved_at`, `resolved_by_staff_id`, `keys_to_activate`, `keys_to_disable` per row. **History = all rows per `equipment_id` ordered by `created_at DESC`.** No schema changes needed for history.

`rfid_key_intended_equipment(rfid_key_id, equipment_id)` — junction table, populated by `configure_key_order_item`. This is the source for "which keys are pending for THIS equipment" (Group 1 of the snapshot).

**Test 092-C** currently passes without the fix — it only asserts `rfid_keys.status = 'active'`, not `key_order_items.status = 'installed'` or `key_orders.status = 'ready_for_pickup'`. Extending 092-C will turn it RED until the migration is applied (correct Strict-TDD behavior).

## Approaches

### Approach 1 — Minimal wire fix only (DB + tests, no UI)
Wire `resolve_equipment_update` to update `key_order_items.status='installed'`. Extend 092-C and add new pgTAP tests. No UI changes.
- Pros: smallest change set, solves the core functional gap, low blast radius.
- Cons: admins still cannot generate the snapshot or see history.
- Effort: Low (1 migration + 1-2 test files).

### Approach 2 — Full bundle (DB fix + snapshot UI + history UI + rollback download)
All items as stated in the change intent. The DB fix is one migration. The UI is three independent slices: (a) pending-keys snapshot panel, (b) history panel, (c) rollback download.
- Pros: complete implementation of the stated flow; admins get the snapshot tool they need.
- Cons: higher total line count; rollback semantics require a product-owner decision; `EquipmentUpdatePanel` snapshot scope bug must be fixed before the snapshot UI can be correct.
- Effort: Medium (1 migration + 2-3 test files + 3-4 UI components + 2 hooks).

### Approach 3 — DB fix + snapshot SQL only (no rollback UI)
Approach 2 without the rollback slice. Deliver the DB fix and snapshot/history UI in one PR, defer rollback.
- Pros: avoids the rollback decision blocker; most valuable pieces delivered together.
- Cons: installer app history/rollback deferred; but installer currently has no history view at all so this is a new gap, not a regression.
- Effort: Medium-low.

**Recommendation: Approach 3** — DB fix + snapshot/history admin UI. The installer rollback UI is optional and depends on whether the product owner needs DB-consistent rollback (Option B — inverse update) or just MDB re-download (Option A). Surface Option A as the default (it costs near-zero: just list resolved rows with MDB download links). Decision needed before investing in Option B.

## Rollback Semantics — decision required

| Aspect | Option A — Re-download only | Option B — Inverse equipment_update |
|---|---|---|
| Mechanism | Admin downloads old MDB from history panel; installer syncs device manually | Generate new equipment_update with keys_to_activate/disable swapped |
| DB state | Diverges from device until next equipment_update corrects it | Stays in sync |
| Validity checks needed | None | Must validate inverse is applicable (key not already picked up, etc.) |
| New code | None beyond listing resolved rows with download links | New RPC + validation logic + UI |
| Complexity | Low | High |

## Pending-Keys Snapshot SQL Shape

No new RPC required — a client-side PostgREST query in `usePendingKeysForEquipment`:

```sql
-- Group 1: to activate
SELECT k.id, k.rfid_code, u.number AS unit_number, 'to_activate' AS "group"
  FROM public.rfid_keys k
  JOIN public.rfid_key_intended_equipment ie ON ie.rfid_key_id = k.id
  JOIN public.units u ON u.id = k.unit_id
 WHERE ie.equipment_id = :equipment_id
   AND k.status = 'pending_installation'
UNION ALL
-- Group 2: to disable
SELECT k.id, k.rfid_code, u.number AS unit_number, 'to_disable' AS "group"
  FROM public.rfid_keys k
  JOIN operations.key_authorizations ka ON ka.rfid_key_id = k.id
  JOIN public.units u ON u.id = k.unit_id
 WHERE ka.equipment_id = :equipment_id
   AND k.status = 'pending_disable'
   AND ka.sync_state = 'installed'
UNION ALL
-- Group 3: unchanged
SELECT k.id, k.rfid_code, u.number AS unit_number, 'unchanged' AS "group"
  FROM public.rfid_keys k
  JOIN operations.key_authorizations ka ON ka.rfid_key_id = k.id
  JOIN public.units u ON u.id = k.unit_id
 WHERE ka.equipment_id = :equipment_id
   AND k.status = 'active'
   AND ka.sync_state = 'installed'
   AND ka.removed_at IS NULL
```

## Blast Radius

The new UPDATE `key_order_items.status = 'installed'` fires the existing `key_order_items_recompute_order_status_trigger`. That trigger calls `recompute_key_order_status(order_id)` — the 4-lane machine. All within the same transaction as `resolve_equipment_update`. The 4-lane machine is idempotent and multi-equipment-safe. No other triggers fire on `key_order_items.status` changes.

The legacy `order_items` branch at line 113 should be preserved unchanged (for in-flight legacy keys). The new `key_order_items` branch is added in parallel.

## Risks

1. **Transaction lock ordering**: `resolve_equipment_update` now holds locks on `rfid_keys` AND `key_order_items` rows within the same transaction. If another transaction updates `key_order_items` concurrently (e.g. admin cancels the order), deadlock is possible. Mitigate by ensuring the order-level lock is taken first in the new migration.
2. **EquipmentUpdatePanel.tsx snapshot scope bug**: the existing `allKeys` prop is building-wide; the snapshot filter must use `rfid_key_intended_equipment` to scope per-equipment. The new `usePendingKeysForEquipment` hook must replace the current filter for correctness.
3. **Test 092-C will go RED** when extended before the migration is applied. This is expected TDD behavior for strict_tdd mode.
4. **Multi-building orders**: the admin must create one `equipment_update` per equipment when an order spans multiple buildings. This is an existing workflow constraint; the fix makes it work correctly (order stays in `pending_installation` until ALL equipment_updates across ALL buildings are resolved).
5. **Rollback Option B complexity**: if the product owner chooses Option B, validating that the inverse is applicable requires checking each key's current state.

## Constraints

- Do NOT modify the 4-lane state machine.
- Do NOT touch the pickup flow — `record_order_key_pickup` remains unchanged.
- Preserve backward compatibility with legacy `order_items` path.
- Keep existing pgTAP suite green.
